### Задание 1

1.1. Бюджетирование проектов, фин. отчеты и прогнозирование рисков
Тип СУБД: Реляционная (SQL) — PostgreSQL или Oracle.
Почему:
Целостность данных (ACID): Требуются строгие транзакции (проводки по бюджетам не должны теряться или дублироваться).
Четкая структура: Финансовые модели имеют жесткую схему (счета, статьи затрат, проекты, суммы).
Сложные аналитические запросы: SQL легко справляется с JOINами, подзапросами и оконными функциями для прогнозирования рисков (например, скользящие средние или тренды).
1.1. Хеширование стало занимать длительное время, какое API можно использовать для ускорения работы?*
Можно использовать API на основе SIMD-инструкций (например, AVX-512) или аппаратное ускорение через Intel QAT (QuickAssist Technology) или GPU-вычисления (CUDA). В программном смысле — использовать библиотеки с векторизованными алгоритмами (например, оптимизированные реализации SHA-256 через OpenSSL EVP).
1.2. Лендинги (сайты) и CRM (маркетинг/продажи)
Тип СУБД: NoSQL (документоориентированная) — MongoDB или Cassandra (для лендингов).
Почему:
Гибкость (Schema-less): Данные по лидам постоянно меняются (то появилось поле "Telegram", то "Предпочтения по цвету"), и менять схему в SQL под каждый новый эксперимент — больно.
Скорость: Документные БД отлично масштабируются горизонтально и быстро пишут/читают JSON-подобные структуры, что идеально для веб-форм на лендингах.
Для CRM: Здесь уже лучше использовать реляционную СУБД (например, PostgreSQL), так как у менеджеров жесткая логика статусов сделок и связи "Клиент -> Сделка -> Задача".
1.2. Можно ли эту задачу закрыть одной СУБД?*
Да, можно. Использовать PostgreSQL с типами данных JSONB.
Реализация: Для лендингов данные пишутся в поле JSONB (сырые данные формы), а для CRM используются стандартные реляционные таблицы. Это дает гибкость (NoSQL внутри) и целостность (SQL снаружи) одновременно.
1.3. База знаний (нормы, правила, обучение)
Тип СУБД: Иерархическая / документная (или даже файловая), но в контексте СУБД — MongoDB или Elasticsearch.
Почему:
Структура компании — это дерево (Отдел -> Департамент -> Должность). Документная модель позволяет хранить вложенные массивы правил.
Главное требование — "простота и понятность структуры". Здесь не нужны сложные связи "многие-ко-многим", достаточно категоризатора.
1.3. Можно ли использовать существующую СУБД из задач выше?*
Да. Если ранее мы выбрали PostgreSQL (с JSONB) для пункта 1.2, то используем её же.
Реализация: Создаем таблицу documents с полями: id, department_tree (JSONB) — путь в иерархии, content (TEXT/JSONB) — сам материал. Индексируем department_tree для быстрого поиска по веткам структуры.
1.4. Логистика (маршруты и курьеры)
Тип СУБД: Графовая — Neo4j или ArangoDB.
Почему:
Ключевое требование: "быстро работать со связями".
Задачи поиска кратчайшего пути (Дейкстра, A*) между объектами и распределение курьеров — это классические графовые алгоритмы. В реляционных БД такие запросы (рекурсивные CTE) работают медленно и сложно пишутся, а в графовых это нативный обход вершин и ребер.
1.4. Подключать ли отдел закупок?*
Лучше сформировать свою (или гибрид).
Отдел закупок оперирует остатками, ценами поставщиков и номенклатурой — это классическая реляционная модель (таблицы).
Решение: Оставить Neo4j для логистов (маршруты), а для закупок использовать PostgreSQL.
Связка: Обмениваться данными через API-шлюз или Message Queue (Kafka/RabbitMQ). Когда логист назначает маршрут, он отправляет событие в закупки: "Для объекта Х нужны материалы Y". Закупки подтверждают наличие через свой SQL-запрос.
1.5. Можно ли все задачи решить одной СУБД?*
Да, технически можно. Это будет PostgreSQL.
Почему: Это универсальный солдат.
Для бюджета — стандартные таблицы.
Для лендингов — JSONB.
Для базы знаний — JSONB + полнотекстовый поиск.
Для логистики — расширение pgRouting (надстройка над PostGIS), которое реализует графовые алгоритмы прямо внутри PostgreSQL.
Минус: На очень больших графах (миллионы маршрутов) PostgreSQL будет медленнее Neo4j, но в рамках одной компании этот вариант самый экономичный и простой в администрировании.

### Задание 2

2.1. Пополнение баланса телефона (6 шагов)
Инициация: Пользователь отправляет запрос на сумму X рублей.
Блокировка средств: Платежная система резервирует сумму на счете пользователя (или списывает со счета-источника — карты/кошелька).
Валидация: Проверяется, что номер телефона существует в системе оператора.
Начисление (внешнее): Отправляется запрос в биллинг оператора на увеличение лицевого счета абонента.
Фиксация списания: В банке/системе происходит окончательное списание средств (Decrease balance).
Коммит: В CRM или истории транзакций создается запись об успешном пополнении, статус транзакции меняется на "Completed".
2.1. Автоплатёж*
Действия аналогичны, но шаг 1 пропускается (инициация ручная).
Добавляется шаг 0 (Триггер): Система в заданное время проверяет баланс абонента.
Условие: Если баланс ниже порога, запускается попытка платежа.
Важное отличие: При автоплатеже добавляется Retry-механизм (повторные попытки через 5, 30, 60 минут в случае ошибки) и Нотификация (пользователь получает SMS "Списан автоплатеж").

### Задание 3

3.1. Пять преимуществ SQL-систем перед NoSQL
Гарантия ACID: Строгая атомарность и согласованность (идеально для финансов).
Стандартизированный язык (SQL): Единый синтаксис запросов, который знают все аналитики, не зависящий от вендора.
Жесткая схема (Контроль типов): Предотвращает попадание "мусорных" данных (ошибка на этапе вставки, а не при чтении).
Сложные транзакционные JOIN-ы: Возможность связать 5-10 таблиц в одном запросе без написания процедурного кода.
Зрелость и инструментарий: Миллион инструментов для мониторинга, бэкапов (PITR) и репликации, протестированных десятилетиями.
3.1. Преимущества NewSQL*
Перед SQL: NewSQL сохраняет ACID и SQL-синтаксис, но добавляет горизонтальное масштабирование (Sharding), как у NoSQL. Классические SQL-машины (Oracle/DB2) масштабируются вертикально (дорого), а NewSQL (Google Spanner, CockroachDB, TiDB) — горизонтально.
Перед NoSQL: NewSQL дает сильную согласованность данных (в отличие от "Eventual Consistency" многих NoSQL), что критично для банковских переводов, при этом сохраняя высокую производительность на огромных кластерах.

### Задание 4

Критерий выбора типа СУБД
Главный критерий — согласованность vs. доступность (CAP-теорема) и модель данных.
Если вычисления — это аналитика (OLAP) по истории (мало изменений, много чтения и агрегации) — берем MPP (Massively Parallel Processing) системы, например, Greenplum или ClickHouse (колоночные).
Если вычисления требуют мгновенных ответов на запросы и высокой доступности (OLTP) — берем NoSQL (Cassandra / ScyllaDB) с моделями распределенных таблиц.
Модель распределенных вычислений
Лучше всего справится парадигма MapReduce или Spark (In-Memory вычисления) в связке с HDFS (Hadoop Distributed File System).
Почему:
Data Locality: На 1000 машинах данные лежат локально. Вместо того чтобы гнать данные к коду (как в классической БД), мы двигаем код к данным (Task Trackers).
Отказоустойчивость: Система автоматически реплицирует данные (минимум 3 копии) на разные машины. При падении одного узла вычисления перезапускаются на другом.
Линейное масштабирование: Прирост производительности прямо пропорционален количеству добавленных машин (чем больше машин, тем быстрее считаем гигабайты данных).
